# Aviation Analytics

Учебный проект по дисциплине «Прогнозно-аналитические системы», профиль «Управление данными».

**Тема:** прогнозно-аналитическая система мониторинга и прогнозирования числа рейсов и доли задержек в аэропортах США.

Система получает сведения о рейсах и погоде, формирует аналитическую витрину, проверяет качество данных, строит прогноз на один день вперёд и представляет результаты в Power BI. Дополнительно реализованы каталог метаданных, lineage, общий журнал выполнения и история изменений Gold.

## Предметная область и показатели

Пользователь системы — аналитик или специалист службы планирования аэропорта. Аналитический интерфейс позволяет сравнивать аэропорты, исследовать динамику рейсов и задержек, просматривать результаты прогнозирования и контролировать обработку данных.

Аэропорты: **ATL, DFW, JFK, LAX, ORD**. Исторический период: **01.01.2023–31.12.2025**. Суточная витрина содержит **5480 строк**, по 1096 дат на аэропорт.

| Показатель | Определение |
|---|---|
| `total_flights` | Число рейсов в исходном наборе для аэропорта и даты, включая отменённые |
| `completed_flights` | Число рейсов, не отмеченных как отменённые; перенаправленные рейсы могут входить в эту группу |
| `cancelled_flights` | Число отменённых рейсов |
| `delayed_flights` | Число неотменённых рейсов с задержкой вылета не менее 15 минут |
| `delay_share` | `100 * delayed_flights / completed_flights`, проценты |

Перенаправления не являются отдельной непересекающейся группой относительно `completed_flights`. Их нельзя повторно прибавлять к общему числу рейсов.

## Источники

- [BTS TranStats](https://www.transtats.bts.gov/) — Reporting Carrier On-Time Performance, помесячные ZIP-архивы с CSV. Используется охват выбранного набора внутренних рейсов, а не всех полётов США.
- [Open-Meteo Historical Weather API](https://open-meteo.com/en/docs/historical-weather-api) — почасовые архивные погодные наблюдения, REST API, JSON.

Исходные файлы сохраняются в `data/raw/`; этот каталог не включается в Git.

## PostgreSQL и миграции

Для финальной конфигурации используется один механизм применения схемы — `src.migrations`. Перед первым развёртыванием убедитесь, что в `docker-compose.yml` **нет** автоматического выполнения той же папки миграций через строку `./sql:/docker-entrypoint-initdb.d:ro`. Постоянный том `postgres_data` сохраняется.

```powershell
docker compose up -d
docker compose ps
python -m src.migrations
python -m src.migrations
```

Дождитесь готовности PostgreSQL перед выполнением миграций. При повторной проверке новых миграций быть не должно. Версии регистрируются в `meta.schema_migrations` после успешного выполнения.

В финальном `src/migrations.py` выполнение SQL-файла в `apply_migration` использует:

```python
connection.exec_driver_sql(sql, execution_options={"no_parameters": True})
```

Это необходимо для SQL-функций миграции 013, содержащих PostgreSQL `format('%s', ...)`.

Проверочные запросы из `docs/check_*.sql` выполняются отдельно. Не помещайте их в `sql/`: мигратор рассматривает SQL-файлы этой папки как миграции.

Не удаляйте рабочий Docker volume для повторной проверки запуска.

## Прогнозные модели и оценка

Горизонт — один день. Признаки включают аэропорт, календарь, лаги 1/7/14/28 дней, скользящие средние 7/28 дней и историческую погоду. Все исторические признаки сдвинуты относительно прогнозируемого дня; фактическая погода прогнозируемого дня не используется. Всего 33 признака.

| Выборка | Период | Записей |
|---|---|---:|
| Обучение | 29.01.2023–31.12.2024 | 3515 |
| Валидация | 01.01.2025–30.06.2025 | 905 |
| Тест | 01.07.2025–31.12.2025 | 920 |

Модель выбирается по MAE на валидации. После выбора CatBoost обучается на train + validation для независимой оценки на тесте. Отдельные модели на всей истории используются для следующего прогноза.

| Цель | Модель | Тестовая MAE | Тестовая RMSE | Выбрана по валидации |
|---|---|---:|---:|---|
| Число рейсов | Seasonal Naive 7 | 27.2424 | 61.4755 | Да |
| Число рейсов | CatBoost | 27.0882 | 46.7381 | Нет |
| Доля задержек | Seasonal Naive 7 | 10.1624 | 14.7364 | Нет |
| Доля задержек | CatBoost | 6.3320 | 9.6339 | Да |

Ошибки числа рейсов измеряются в рейсах; ошибки доли — в процентных пунктах. Для доли задержек CatBoost уменьшает MAE примерно на 37.7% относительно baseline. Небольшое преимущество CatBoost по тестовой MAE числа рейсов не использовалось для пересмотра выбора после тестирования.

Оценка соответствует последовательному прогнозу на один день с наблюдаемой историей до предыдущего дня, а не многодневному прогнозу из одной точки.

## Контроль качества

```powershell
python -m src.quality
python -m src.quality --demo
```

Проверяются типы, полнота, уникальность, диапазоны, формулы, ссылочная целостность и покрытие настроенного периода. Результаты сохраняются в `meta.quality_runs`, `meta.quality_results` и `reports/quality/`.

Критические нарушения и ошибки выполнения проверок блокируют прогнозирование. Демонстрация использует временные данные: отдельные `FAIL` ожидаемы, итог `DEMO OK` подтверждает успешность проверки. Демонстрационные журналы исключены из рабочих BI-представлений.

Актуальность проверяется относительно заданного архивного периода, а не относительно сегодняшней даты. `PASS` не означает наличие рейсов за текущий месяц.

## История Gold

```powershell
python -m src.history check
python -m src.history demo
python -m src.history check
```

`gold.airport_daily_history` содержит версии состояний. `BASELINE` создаётся при внедрении миграции на уже заполненной базе. Изменение содержательных значений создаёт новую версию; изменение только `updated_at` и повтор тех же значений — нет. Числовое сравнение нормализуется до 8 знаков после запятой, снимки хранят исходные значения.

Удаления фиксируются как `DELETE`, повторные вставки — `INSERT`. Откат отменяет изменение и его версию. `flight_date` — дата рейсов; `valid_from`/`valid_to` — время фиксации состояния системой. История не восстанавливает неизвестные прошлые состояния.

Демонстрация ожидает последовательность числа временных версий **1 → 1 → 2 → 2 → 2 → 3 → 4**. Рабочие Gold и история не изменяются. Сохраняется отдельный демонстрационный журнал запуска.

На исходной проверенной базе: 5480 Gold-строк, 5480 начальных версий и нулевые нарушения. На чистой базе с уже установленными триггерами первое наполнение Gold создаст `INSERT`, а не `BASELINE`; это корректное отличие порядка развёртывания. Количество исторических версий также может увеличиваться при реальных изменениях данных.

В финальном `src/history.py` CLI использует единый импортируемый модуль, чтобы контекст демонстрации совпадал с контекстом `PipelineRun.step`:

```python
if __name__ == "__main__":
    from src.history import main as history_main
    raise SystemExit(history_main())
```

Для исходного эксперимента до новых пакетов: 1 эксперимент, 48 метрик, 7300 backtest-строк, 2 пакета и 40 прогнозов.

При изменении истории обучения модуль может остановиться из-за несовпадения снимка. Не отключайте проверку: выясните причину изменения и при необходимости явно переобучите модель.

## Ограничения

- Учебный прототип, пять аэропортов, фиксированный архив 2023–2025.
- BTS публикует сведения с задержкой; прогноз предполагает доступность истории до предыдущего дня.
- Исходная дата прогноза — **01.01.2026**, дата истории — **31.12.2025**. Это не прогноз на завтра относительно текущей даты.
- Используются исторические погодные признаки; оперативный погодный прогноз не подключён.
- Не все причины задержек представлены в данных. Сопоставление погоды и задержек не доказывает причинность.
- Историзация фиксирует изменения, дошедшие до Gold; механизм автоматической замены исправленных внешних архивов не реализован.
- Импортированные журналы Power BI требуют Refresh.
- Расписание запуска, облачное размещение и контейнеризация Python не заявляются как реализованные.
- Развёртывание на чистом окружении проверяется отдельно по этой инструкции; успешный запуск на заполненной рабочей базе не заменяет такую проверку.
